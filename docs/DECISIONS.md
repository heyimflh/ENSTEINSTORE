# ENSTEINSTORE — Architecture Decision Record & Decision Log

Dokumen ini mencatat seluruh keputusan arsitektural, teknis, dan resolusi ketidakcocokan antara PRD dan frontend yang sudah ada, serta temuan audit teknis pada Fase 0.

---

## 1. Keputusan Inti Resolusi (Master Prompt K1 – K14)

| ID | Konteks / Isu | Keputusan | Alasan & Dampak Teknis |
|---|---|---|---|
| **K1** | Tipe pergerakan inventory di mock frontend berbeda (`IN`, `ADJUSTMENT`, `OUT_ORDER`, `RESERVE`) | Backend memakai 7 tipe resmi PRD §12.2: `STOCK_IN`, `ONLINE_RESERVE`, `ONLINE_SALE_OUT`, `RESERVATION_RELEASE`, `OFFLINE_SALE_OUT`, `ADJUSTMENT_IN`, `ADJUSTMENT_OUT`. Frontend diubah mengonsumsi 7 tipe ini. | Menjaga audit trail yang presisi dan kompatibel 100% dengan trigger PostgreSQL di database. |
| **K2** | Status payment customer di mock frontend mencakup `UNPAID`, `CANCELLED`, `FAILED` yang tidak cocok dengan PRD §11.2 | Database dan API menggunakan 5 status resmi PRD: `PENDING`, `WAITING_VERIFICATION`, `PAID`, `REJECTED`, `EXPIRED`. Adapter frontend memetakan `UNPAID -> PENDING`. Pada pembatalan manual, status order menjadi `CANCELLED` dan payment menjadi `EXPIRED` serta mencatat `cancellation_reason`. Pada simulasi pembayaran gagal, status payment tetap `PENDING` dengan payload respons `{ outcome: "FAILED" }` (stok tetap terreservasi, sesuai TC-12). | Memastikan integritas state machine dan reservasi stok tetap konsisten. |
| **K3** | Metode pembayaran di mock frontend vs PRD | Database menyimpan enum: `BANK_TRANSFER`, `E_WALLET`, `SIMULATED`, `CASH`. Pemetaan: UI bank -> `BANK_TRANSFER`, ewallet/QRIS -> `E_WALLET`, cod -> `CASH`, ditambah opsi "Simulasi" (mode demonstrasi/pengujian) di halaman pembayaran. Pada transaksi offline admin: TUNAI -> `CASH`, QRIS -> `E_WALLET`, TRANSFER -> `BANK_TRANSFER`. | Mendukung kebutuhan demonstrasi akademik dan operasional riil toko. |
| **K4** | Field di luar PRD pada frontend (`shippingCourier`, `trackingNumber`, `discount`, `rating`, `variant`, `location`, `Pack` unit) | TIDAK dimodelkan di backend (sesuai batasan Out-of-Scope PRD §4.2). Frontend menyembunyikan atau mengisi nilai default pada adapter. Tidak ada kolom database tambahan untuk atribut-atribut ini. | Mencegah perluasan scope (scope creep) dan menjaga skema 3NF tetap bersih. |
| **K5** | Field alamat checkout di frontend (nama, telepon, email, kota, kecamatan, kodepos, catatan) | Backend hanya menyimpan: `recipientName`, `recipientPhone`, `fulfillmentMethod`, `deliveryAddress`, `notes`, `paymentMethod`. Frontend menggabungkan `address`, `city`, `district`, `postalCode` menjadi satu string `deliveryAddress`. Kolom `orders.notes` ditambahkan ke skema DB. | Menjaga kesederhanaan model pengiriman internal toko tanpa dependensi sistem kurir eksternal. |
| **K6** | Batas bayar & biaya pengiriman hardcoded di frontend (Rp15.000, 24 Jam) | Dipindahkan menjadi konfigurasi terpusat di backend (`application.yml`: `app.payment.expiry-hours=24`, `app.delivery.fee=15000`). Frontend mengambilnya via endpoint publik `GET /api/store/config`. Frontend dilarang keras melakukan hardcode. Kolom `orders.payment_deadline` ditambahkan ke skema DB. | Fleksibilitas bisnis bagi pemilik toko tanpa perlu deploy ulang frontend. |
| **K7** | Rekening bank dan e-wallet toko di halaman payment frontend | Dikonfigurasikan di backend `application.yml` (`app.payment.bank-accounts[]`, `app.payment.ewallets[]`) dan diekspos melalui `GET /api/store/config`. Nilai awal mengambil data ilustrasi dari halaman payment frontend dengan label "data ilustrasi". | Sentralisasi konfigurasi bisnis dan konsistensi data. |
| **K8** | Penentuan produk Featured, New, dan Terpopuler | Ditambahkan kolom `products.is_featured BOOLEAN` (dikelola oleh admin). Nilai `isNew` diturunkan dari kondisi `created_at <= CURRENT_TIMESTAMP - INTERVAL '30 days'` (dapat dikonfigurasi). Nilai `salesCount` diturunkan dari agregasi SUM `order_items.quantity` pada pesanan yang sudah berstatus lunas. | Menghindari redundansi data transaksi sekaligus memberi kontrol kurasi featured item kepada admin. |
| **K9** | Skema ID dan lookup entitas | Primary Key seluruh entitas inti menggunakan UUID (PRD §13.5). Endpoint detail produk `GET /api/products/{idOrCode}` menerima UUID atau `product_code`. Endpoint detail order `GET /api/orders/{idOrNumber}` menerima UUID atau `order_number` (tanpa prefix `#`). Respons JSON selalu menyertakan `id` (UUID) dan identifier bisnis (`code` / `orderNumber`). | Kompatibel dengan URL frontend yang sudah ada (`/products/PRD-BHN-001`, `/orders/EST-20261115-0042`) tanpa mengorbankan UUID PK. |
| **K10** | Pengelolaan satuan (Unit) | Seed database awal: Meter (`m`, `allow_decimal = true`), Pcs (`pcs`, `allow_decimal = false`), Roll (`roll`, `allow_decimal = false`). Kolom `unit` di respons API menggunakan `lower(unit_name)` agar cocok dengan union tipe frontend `'meter' \| 'pcs' \| 'roll'`. Tipe frontend dilonggarkan menjadi `string` agar satuan baru dari admin tidak merusak UI. Respons API juga menyertakan `unitName`, `unitSymbol`, dan `allowDecimal`. | Memenuhi aturan desimal kain (2.5 meter) dan non-desimal (pcs) sekaligus memberi ruang ekspansi unit. |
| **K11** | Format dan ukuran upload file | Bukti transfer: JPG, PNG, WEBP, ukuran maksimum 2 MB. Foto produk: JPG, PNG, WEBP, ukuran maksimum 2 MB. Validasi wajib di backend: ekstensi file + MIME type + verifikasi magic bytes. File disimpan dengan nama acak UUID di direktori luar webroot untuk mencegah path traversal dan eksekusi file berbahaya. | Keamanan upload file (OWASP) dan kompatibilitas format gambar web modern (WEBP). |
| **K12** | Autentikasi token JWT dan Logout | JWT Bearer token pada header `Authorization`, TTL default 8 jam (konfigurabel via env/yml), klaim memuat `sub` (user_id), `role`, `email`, dan `jti` (UUID unik). Logout (FR-03) menyimpan `jti` ke tabel `revoked_tokens` dengan masa kedaluwarsa. Filter keamanan memeriksa blacklist token ini. Registrasi publik hanya dapat membuat akun dengan role `CUSTOMER`. Akun `ADMIN` dibuat eksklusif melalui seed database dan env. | Keamanan stateless JWT dengan kapabilitas invalidasi token instan (revocation). |
| **K13** | Basis tanggal dan zona waktu pelaporan | Seluruh pelaporan bisnis menggunakan zona waktu `Asia/Jakarta` (`UTC+07:00`) berbasis kolom `orders.order_date`. Kriteria order "terjual" untuk laporan penjualan adalah: `payment_status = 'PAID'` DAN `order_status <> 'CANCELLED'`. Mencakup transaksi `ONLINE` dan `OFFLINE`. | Akurasi pembukuan dan sinkronisasi 100% antara laporan penjualan dan total order lunas. |
| **K14** | Format respons error terstandarisasi | Mengikuti PRD §15.9 dengan tambahan atribut `code` (UPPER_SNAKE_CASE) dan `fieldErrors: [{ field, message }]` untuk kegagalan validasi form. Pesan ke pengguna dalam Bahasa Indonesia ramah pengguna. Kegagalan login mengembalikan pesan generik "Email atau password salah" (FR-02). | Memudahkan integrasi form frontend dan mencegah kebocoran informasi user enumeration. |

## 2. Temuan Audit Tambahan (Fase 0)

| ID | Isu / Temuan Audit | Keputusan | Alasan & Solusi |
|---|---|---|---|
| **D15** | Inkonsistensi huruf besar/kecil (case-sensitivity) pada path file gambar di `frontend/src/data/products.ts` | File asli di disk menggunakan huruf kapital: `KancingALL.jpeg`, `ElastikALL.jpeg`, `LobiLobiALL.jpg`. Namun kode TypeScript mereferensikan `KancingAll.jpeg`, `ElastikAll.jpeg`, `LobilobiAll.jpg`. | Pada sistem operasi Linux/Docker (case-sensitive), perbedaan ini menyebabkan HTTP 404 (broken image). Path diubah pada seed DB dan frontend menjadi path yang tepat sesuai file di disk. |
| **D16** | Duplikasi folder `public/images` di root repo dan di `frontend/public/images` | Folder `public/images` di root repo akan dihapus atau diabaikan; aset tunggal berpusat di `frontend/public/images`. Backend upload folder dipisahkan ke `backend/uploads/` (di luar repo, dikonfigurasi via env). | Menjaga single source of truth untuk aset statis frontend dan mencegah kerancuan git tracking. |
| **D17** | Baseline framework Spring Boot 4.x & Java 25 | Menggunakan Spring Boot 4.1.2 GA (Jakarta EE 11, Hibernate 7, Jackson 3, Spring Security 7) dengan Java 25 LTS sesuai target PRD. Starters modular: `spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`, `spring-boot-starter-validation`, `spring-boot-starter-security`, `spring-boot-starter-actuator`. | Sesuai dengan spesifikasi PRD §14 dan instruksi Master Prompt. |
| **D18** | Skema pembatasan nomor order atomik | Menggunakan tabel `order_number_counters (order_date DATE PK, last_value INT)` dengan eksekusi query PostgreSQL atomik: `INSERT ... ON CONFLICT (order_date) DO UPDATE SET last_value = order_number_counters.last_value + 1 RETURNING last_value`. Tanggal dihitung dengan `CURRENT_DATE AT TIME ZONE 'Asia/Jakarta'`. Format: `EST-YYYYMMDD-XXXX`. | Menjamin keunikan nomor pesanan bebas race condition tanpa lock tabel besar. |
| **D19** | Penguncian stok dan Choke Point stok tunggal di Java | Java tidak pernah menjalankan query `UPDATE products SET stock_on_hand ...`. Mutasi stok HANYA melalui `INSERT INTO stock_movements` melalui `InventoryService`. Trigger PostgreSQL `trg_apply_stock_movement` bertugas memvalidasi ketersediaan stok, mengunci row produk `FOR UPDATE`, dan memperbarui angka fisik serta reservasi. Upaya update langsung ke kolom stok `products` ditolak oleh trigger penjaga kecuali konfigurasi `app.stock_mutation = 'on'`. | Mencegah duplikasi logika stok antara aplikasi dan DBMS, menjamin integritas ACID bahkan saat ada akses direct DB. |
| **D20** | Simulasi Pembayaran pada Frontend & Backend | Menambahkan endpoint `POST /api/payments/{orderId}/simulate` dengan parameter `{ outcome: "SUCCESS" | "FAILURE" }`. Endpoint ini diproteksi oleh feature flag `app.payment.simulation-enabled` (aktif pada profile `dev`). Di frontend, halaman payment menyajikan tab "Simulasi (Demo)" jika feature flag aktif. | Memenuhi skenario pengujian TC-11, TC-12, dan demonstrasi akademik tanpa integrasi payment gateway eksternal riil. |
| **D21** | Dukungan Lingkungan Docker & Database Lokal | Komputer host saat ini memiliki Java 25 LTS dan Maven 3.9.16. Docker belum terdeteksi aktif pada PATH. Konfigurasi `docker-compose.yml` untuk PostgreSQL 18 disediakan sesuai standar, dan `application.yml` dirancang fleksibel untuk profile `dev` (dapat diarahkan ke Docker postgres:18 lokal maupun instance PostgreSQL lokal port 5432) serta Testcontainers untuk integration testing. | Memungkinkan eksekusi fleksibel pada berbagai lingkungan tanpa terhambat ketiadaan Docker daemon sementara. |
| **D22** | Seed Admin Password | Password admin seed default `EnsteinAdmin2026!` di-hash BCrypt(cost=10) dan disematkan langsung di V13 seed SQL dengan komentar peringatan agar diganti di production via environment variable. Tidak ada tabel `app_settings` atau mekanisme override runtime karena di luar scope PRD. | Kemudahan setup development dengan keamanan yang cukup untuk demo; password di-hash sehingga tidak plaintext di repo. |
| **D23** | V13 Stock via Trigger (tidak via UPDATE langsung) | Seed data di V13 menginsert stock dengan `stock_on_hand = 0` pada INSERT produk, lalu memasukkan `STOCK_IN` stock_movements. Trigger `trg_apply_stock_movement` yang menaikkan `stock_on_hand`. Ini memastikan Rule 7 (AGENTS.md) berlaku sejak seed awal. | Tidak ada exception untuk Rule 7 bahkan pada seed data; audit trail stock tersedia sejak hari pertama. |
| **D24** | Flyway Migration Order V1-V13 | V1: users domain. V2: categories, units. V3: products (depends on V2). V4: carts (depends on V3). V5: orders (depends on V3, V4). V6: payments (depends on V5). V7: stock_movements (depends on V3). V8: views (depends on V5, V7). V9: functions. V10: procedures. V11: triggers. V12: indexes. V13: seed. Urutan ini menghormati dependensi FK dan memastikan fungsi/trigger tersedia sebelum digunakan seed. | Flyway mengeksekusi secara berurutan; setiap migration bersifat idempotent via `ON CONFLICT DO NOTHING`. |
| **D25** | image_url di Seed menggunakan path case-sensitive Linux | Semua path gambar di V13 menggunakan nama file PERSIS sesuai disk: `KancingALL.jpeg` (bukan `KancingAll.jpeg`), `ElastikALL.jpeg` (bukan `ElastikAll.jpeg`), `LobiLobiALL.jpg` (bukan `LobilobiAll.jpg`). Frontend TypeScript juga harus diperbaiki sesuai keputusan ini (dilakukan pada Fase 7 — integrasi frontend). | Mencegah HTTP 404 broken images di lingkungan Linux/Docker production yang case-sensitive. |
| **D26** | PostgreSQL 18 Docker Volume Mount Path `/var/lib/postgresql` | Pada image Docker resmi PostgreSQL 18+, direktori mount volume harus diletakkan pada `/var/lib/postgresql` (bukan `/var/lib/postgresql/data`) agar kompatibel dengan layout direktori berbasis versi mayor (`/var/lib/postgresql/18/docker`) dan pg_ctlcluster/pg_upgrade. | Mencegah kontainer restart loop dan memastikan kompatibilitas native PostgreSQL 18. |
| **D27** | Modular Starter Flyway di Spring Boot 4 (`spring-boot-starter-flyway`) | Pada Spring Boot 4.x, konfigurasi otomatis Flyway dipisahkan dari `spring-boot-autoconfigure` ke starter modular `org.springframework.boot:spring-boot-starter-flyway` bersama `flyway-core` dan `flyway-database-postgresql`. | Memastikan bean `Flyway` terdaftar otomatis oleh Spring Boot IoC container. |
| **D28** | Proteksi JPA Updatable=False untuk Kolom Stok Produk | Atribut `stockOnHand` dan `reservedQuantity` pada `Product` entity dipetakan dengan `updatable = false`. Hal ini mengunci Hibernate agar tidak pernah menyertakan kedua kolom ini dalam query `UPDATE products SET ...`. Satu-satunya jalur mutasi fisik & reservasi stok adalah trigger PostgreSQL via `INSERT INTO stock_movements`. | Menjamin penegakan aturan Rule 7 (AGENTS.md) secara mutlak di tingkat abstraksi JPA/ORM. |
| **D29** | Pembaruan Hash Password Admin Seed (V14) | Nilai hash password admin awal di V13 digantikan via migrasi `V14__fix_admin_password_hash.sql` menggunakan hash BCrypt(cost=10) valid untuk password default `EnsteinAdmin2026!` (`$2a$10$N31NTmtOgkA3I0rUiHApJefC.t110kDuAtmdKvT7hh4.y8.I1Y9Jq`). | Menjamin akun seed admin dapat langsung login secara mulus baik pada pengujian integrasi maupun environment pengembangan/demo. |
| **D30** | Manajemen Transaksi pada AuthIntegrationIT | Kelas pengujian `AuthIntegrationIT` tidak menggunakan anotasi `@Transactional` di level kelas. Pasalnya, `AuthenticationManager.authenticate()` mengeksekusi autentikasi melalui `CustomUserDetailsService` pada transaksi terpisah; jika kelas test dibungkus `@Transactional`, registrasi user pada method test yang sama belum ter-commit di PostgreSQL (`READ_COMMITTED`), sehingga memicu 401 palsu. Kebersihan dan idempotensi data pengujian dijamin via `@BeforeEach` cleanup SQL manual. | Memastikan integritas pengujian alur autentikasi dan otorisasi end-to-end yang realistis terhadap database PostgreSQL sesungguhnya. |
| **D31** | Pemisahan Pengujian Surefire vs Failsafe | `EnsteinStoreApplicationTests` diubah menjadi `EnsteinStoreApplicationIT` agar dieksekusi oleh Maven Failsafe Plugin bersama profile `integration-test`. Surefire hanya menjalankan unit test murni yang terisolasi dari database, sedangkan seluruh integrasi DB dan konteks penuh dijalankan saat fase `verify`. | Memisahkan siklus pengujian cepat (unit test) dari pengujian integrasi berfasilitas database PostgreSQL asli secara bersih dan deterministik. |
| **D32** | Penegakan Single Choke Point Mutasi Stok & Sinkronisasi Cache JPA | Seluruh mutasi stok dieksekusi eksklusif melalui `InventoryService` dengan `INSERT INTO stock_movements` (tipe: `RESERVE`, `UNRESERVE`, `FULFILLMENT`, `SALE`, `STOCK_IN`, `ADJUSTMENT`, `RETURN`) yang mengaktifkan trigger PostgreSQL `trg_apply_stock_movement`. Karena kolom stok pada entitas `Product` dikunci dengan `updatable = false` (D28), sesi persistensi JPA pada pengujian disinkronisasi melalui `entityManager.flush()` dan `entityManager.clear()` sebelum pembacaan ulang nilai stok teraktual. | Memenuhi Aturan Utama 7 (AGENTS.md) secara mutlak tanpa inkonsistensi cache first-level Hibernate. |
| **D33** | Pola Desain Strategy Pattern untuk Payment Processors | Pemrosesan pembayaran dirancang menggunakan interface `PaymentProcessor` dengan tiga implementasi: `ManualTransferProcessor` (Transfer Bank & E-Wallet dengan pengunggahan bukti bayar menuju `WAITING_VERIFICATION`), `SimulatedPaymentProcessor` (simulasi demo `SUCCESS` vs `FAILED` sesuai K2 & TC-12), dan `CashPaymentProcessor` (pembayaran tunai toko fisik langsung `PAID`). | Memenuhi PRD §19.1 dan memudahkan penambahan metode pembayaran baru di masa mendatang tanpa mengubah logika inti. |
| **D34** | Penyelarasan Constraint Penjualan Offline (IN_STORE) | Transaksi penjualan langsung toko fisik (offline) wajib memiliki `order_type = OFFLINE`, aktor `created_by_admin_id`, dan metode `fulfillment_method = IN_STORE` guna memenuhi database check constraint `chk_offline_needs_admin`. | Menjaga konsistensi data penjualan kasir fisik vs pengantaran/pickup online. |
| **D35** | Pemrosesan Paralel Ringkasan Dashboard (Multithreading) | `DashboardService` mengeksekusi 3 query terpisah (ringkasan penjualan, ringkasan stok, dan 5 pesanan terkini) secara paralel menggunakan `CompletableFuture` dengan `ThreadPoolTaskExecutor` terkelola (`dashboardExecutor`). | Memenuhi persyaratan arsitektur multithreading (PRD §8.8, AGENTS.md §4) dengan latensi agregasi minimal. |
| **D36** | Proteksi CSV Injection & UTF-8 BOM pada Ekspor Laporan | `CsvReportExporter` melakukan sanitasi otomatis dengan menambahkan awalan petik tunggal (`'`) pada setiap sel yang diawali karakter formula (`=`, `+`, `-`, `@`, `\t`, `\r`) serta menyertakan UTF-8 BOM (`0xEF`, `0xBB`, `0xBF`) untuk kompatibilitas tampilan karakter di Microsoft Excel. | Mencegah eksploitasi Spreadsheet Formula Injection (CWE-1236) dan menjamin keakuratan format data ekspor. |
| **D37** | Dynamic Filtering & Specification JPA pada Katalog Produk | `ProductService.getProducts` menggunakan Spring Data JPA `Specification<Product>` untuk mendukung pencarian kombinasi kata kunci (nama & kode), kategori (ID & slug), produk unggulan (`isFeatured`), produk baru (`createdAt >= now - 14d`), dan sorting fleksibel (`terbaru`, `harga-rendah`, `harga-tinggi`, `terpopuler`). | Menghilangkan duplikasi query repository dan menyediakan API pencarian yang fleksibel bagi frontend. |
| **D38** | Standardisasi PagedResponse Generic DTO | Menggunakan `PagedResponse<T>` (`content`, `page`, `size`, `totalElements`, `totalPages`, `last`) sebagai kontrak seragam respon paginasi di seluruh endpoint katalog, pesanan, inventaris, dan pembayaran. | Menjamin konsistensi struktur data yang diproses oleh TanStack Query di presentation layer Next.js. |
| **D39** | Endpoint POS Offline Sales Terdedikasi | `POST /api/admin/offline-sales` memproses transaksi langsung kasir toko fisik secara atomik dengan `fulfillment_method = IN_STORE`, order `COMPLETED`, pembayaran `PAID`, serta pemotongan stok otomatis via trigger database `SALE`. | Memenuhi PRD §8.7 dan TC-15 dengan jaminan check constraint `chk_offline_needs_admin`. |
| **D40** | Ekspor Streaming Laporan CSV Terproteksi | `AdminReportController` menuliskan data CSV langsung ke `HttpServletResponse.getOutputStream()` dengan header `Content-Type: text/csv; charset=UTF-8` dan `Content-Disposition: attachment`. | Menghindari konsumsi memori berlebih di heap server untuk ekspor dataset laporan berukuran besar. |
